## 一、项目背景与设计约束

### 1.1 项目背景

本课程设计要求在**前后端分离**架构下，完成电子商务平台**前端系统**的设计与实现。前端系统需同时支撑两条业务线：

- **后台管理子系统**：面向系统管理员，负责商品类型、商品信息、订单与数据的全量管理；
- **电商前台子系统**：面向注册用户与非注册游客，负责商品浏览、搜索、交易与个人中心。

前端在前后端分离架构中的定位是：**唯一的人机交互入口 + 业务状态编排层 + 接口聚合层**。它不承担业务规则的最终裁决（那是后端的职责），但需要负责路由权限控制、交互流程串联、请求鉴权、前端数据加工与可视化呈现。

本次设计采用 **纯前端 + Mock 数据** 的方式独立完成前端系统，通过 Mock 层模拟后端 REST 接口，保证前端工程可独立开发、独立演示、独立验收。

### 1.2 设计约束（已确认的技术决策）

| 决策项 | 结论 | 说明 |
| --- | --- | --- |
| 数据来源 | 纯前端 + Mock | 不依赖真实后端，Mock 与业务代码解耦，未来可一键切真实接口 |
| 构建工具 | Vite 5+ | 启动快、原生 ESM、零冗余配置 |
| 框架 | Vue 3.4+ | 组合式 API + `<script setup>` |
| 语言 | JavaScript + JSDoc | 不使用 TypeScript，用 JSDoc 补充类型提示 |
| 路由 | Vue Router 4 | `createWebHistory`，动态路由 + meta 鉴权 |
| 状态管理 | Pinia 3 | 统一 setup store 写法（pinia 2 与 persistedstate 4 存在 peer 冲突，故用 3） |
| UI 组件库 | Element Plus | **全量注册 + 全局样式**（`app.use(ElementPlus, { locale: zhCn })`） |
| 数据可视化 | ECharts 5（用 useEcharts 组合函数封装实例生命周期） | 数据统计模块 |
| 网络请求 | Axios | 单例封装 + 拦截器 |
| 质量工具 | ESLint + Prettier | 统一代码风格（P5 阶段接入） |

### 1.3 角色与权限矩阵

| 角色 | 标识 | 可访问区域 | 典型能力 |
| --- | --- | --- | --- |
| 系统管理员 | `admin` | `/admin/*` | 商品类型 / 商品 / 订单全量管理，数据统计 |
| 注册用户 | `user` | 前台 + 用户中心 | 浏览、搜索、加购、下单、收藏、个人信息管理 |
| 非注册游客 | `guest` | 前台公开页 | 仅浏览 / 搜索 / 查看详情；交易类操作被拦截并跳转登录 |

路由元信息统一约定：

```js
meta: {
  title: '页面标题',        // 面包屑与 document.title
  requiresAuth: true,      // 是否需要登录
  role: 'admin' | 'user',  // 需要的角色
  keepAlive: false,        // 是否缓存组件
  icon: 'Goods'            // 菜单图标（后台）
}
```

### 1.4 统一接口契约

所有接口统一响应结构，便于拦截器统一解包：

```json
{ "code": 0, "message": "success", "data": {} }
```

- `code === 0` 表示成功；其余为业务错误码，集中维护在 `utils/constants.js` 的 `ERROR_MAP`；
- 请求拦截器负责注入 Token、开启 loading；响应拦截器负责解包 `data`、失败提示、`401` 清 Token 跳登录。

### 2.2 分层模型（三方案共用的心智模型）

```
┌─────────────────────────────────────────────┐
│  页面层 views/        路由对应的页面级组件      │
├─────────────────────────────────────────────┤
│  组件层 components/   通用组件 + 业务组件       │
├─────────────────────────────────────────────┤
│  状态层 store/        Pinia，跨页面共享状态     │
├─────────────────────────────────────────────┤
│  逻辑层 composables/  可复用的组合式逻辑        │
├─────────────────────────────────────────────┤
│  接口层 api/          Axios 封装 + 接口定义     │
├─────────────────────────────────────────────┤
│  数据层 mock/（开发期） 自研 Vite Mock 中间件 + 确定性种子数据 │
└─────────────────────────────────────────────┘
```

三套方案的差异，本质上是**这条分层的"物理切分粒度"不同**：方案一在同一工程内用目录切分；方案二用包（package）切分；方案三用独立的运行时应用切分。

### 3.4 Pinia 模块划分

| store | 关键 state | 关键 action / getter | 持久化 |
| --- | --- | --- | --- |
| `user` | token、role、profile | login / logout / fetchProfile；`isAdmin` / `isLogin` | token 持久化 localStorage |
| `app` | sidebarCollapsed、theme | toggleSidebar / setTheme | 持久化 |
| `cart` | items[]、count | add / updateQty / remove / clear；`totalPrice` / `totalCount` | 游客本地持久化，登录后合并 |
| `category` | list、loaded | fetchList（带缓存）；`options` getter | 会话级可持久化 |
| `goods` | query、list、total、detailCache | setQuery / resetQuery / fetchList / fetchDetail | 不持久化 |
| `order` | confirmItems、query、list | setConfirmItems / clearConfirm / fetchList | confirm 暂存 sessionStorage |

原则：**跨子系统共享 `user` / `app` / `category`**；`goods` / `order` 在 admin 与 before 语义下用命名空间化 action（如 `fetchAdminList` / `fetchFrontList`）区分，避免拆得过碎。

### 3.5 Mock 层设计

- **选型**：自研 Vite Mock 中间件 `build/mock-server-plugin.js`，挂到 Vite dev server（**dev-only、业务代码零侵入**）。它由 **Node 原生 ESM 直接 `import()`** 加载 mock 模块，具备热重载能力；`json-server` 作为可选加分项（真实 REST + 进程级持久化，但需额外进程）。
- **数据生成**：**不使用 Mock.js 随机造数**，而是自研「确定性种子生成器」（基于固定种子的伪随机），原因：统计模块要做**多表关联聚合**，商品 ↔ 类型 ↔ 订单之间必须能真实对上，随机数据会让图表失去意义；固定种子同时保证每次启动数据一致、便于截图与测试复现。
- **目录组织**：`mock/modules/*.js` 按业务域拆分（每个文件默认导出一个 MockMethod 数组，共 8 个模块 / 34 个接口）；`mock/db.js` 维护内存表（users / categories / goods / orders / favorites / banners）与 `globalThis` 单例；`mock/helpers.js` 提供统一响应契约、分页、Token 解析。
- **存储位置**：Mock 运行在 **Node（dev server）进程**内，没有 `localStorage`；数据存活于进程内存——**浏览器刷新不丢，重启 dev server 才重置**为种子数据。
- **⚠️ 为什么弃用 `vite-plugin-mock`（实证教训）**：它内部用 `bundle-require` 把每个 mock 文件打包成 `_xxx.bundled_*.mjs` 写到**源文件同级目录**，再 require、再**删除**。这在受限环境下有两个硬伤：
  1. 产物落在被 glob 的目录里，不排除就会随热重载**逐轮翻倍**（实测产生 **383 个**临时文件、4.2 MB，文件名出现 4 层嵌套 `bundled`）；
  2. 它依赖「删除文件」这一动作，一旦删除被安全策略拦截，**整个 mock 层当场失效**（表现为 `/api/*` 全部返回 HTML 而非 JSON）。
  自研中间件从设计上消除了这两个问题：**零临时文件、零删除操作**。若将来换回第三方 mock 插件，务必先确认它是否会把产物写回被扫描的目录。
- **与 axios 解耦（关键）**：
  1. `api/*.js` 只调用 `request.get('/goods/list')`，**完全不感知 mock 存在**；
  2. `request.js` 的 `baseURL = import.meta.env.VITE_API_BASE`；
  3. mock 插件仅在 `command === 'serve' && VITE_USE_MOCK === 'true'` 时加载；
  4. **切真实接口只需两步**：关闭 `.env` 中 `VITE_USE_MOCK`、把 `VITE_API_BASE` 指向真实域名，业务代码零改动。

### 3.6 组件复用策略

| 层级 | 组件 | 复用范围 |
| --- | --- | --- |
| `common/` 通用展示层 | DataTable、FormDialog、SearchForm、Pagination、ImageUpload、StatusTag、EmptyState | **后台与前台都可复用** |
| `admin/` 业务层 | HeaderCom、SidebarCom、StatCard | 仅后台 |
| `before/` 业务层 | HeaderCom、FooterCom、CarouselCom、CategoryNav、GoodsCard、SpecSelector | 仅前台 |
| `composables/` 逻辑层 | useTable、useDialog、useAuth、useEcharts | 跨子系统复用 |

**划分原则**：有业务语义 / 绑定特定接口 → 业务组件；纯 UI + props/emit 驱动 → `common`。跨子系统复用一律走 `common` 与 `composables`。

### 3.7 关键技术点（对应报告 3.3）

1. **路由分区 + 嵌套路由 + 全局守卫鉴权**：meta 驱动登录态与角色拦截，动态菜单由路由表生成；
2. **axios 拦截器 + Mock 拦截 + 统一响应契约**：一套 `request.js` 支撑双系统，Mock 与真实接口一键切换；
3. **`useTable` / `useDialog` 组合函数抽象**：后台四类列表复用同一套「筛选 + 分页 + CRUD + 弹窗」逻辑；
4. **ECharts 多表关联聚合**：基于 mock db 做「按月销量」「按类型订单」聚合，演示前端数据加工能力；
5. **UI 库引入策略（全量注册 vs 按需引入）**：本方案选择 `app.use(ElementPlus, { locale: zhCn })` + 全局 `index.css` 的**全量注册**，而非 `unplugin-vue-components` + `ElementPlusResolver` 的按需引入，理由是：
   - 既然已 `app.use(ElementPlus)`，整个组件库无论如何都会进入产物，按需解析器能省的**只有 CSS**；
   - 解析器会为每个用到的组件再注入一份 `element-plus/es/components/*/style/css`，与全局 `index.css` **重复**；同时让 Vite 依赖预构建不断「发现新依赖 → 重新预构建」；
   - 重新预构建需要清理 `.vite` 缓存目录，在受限环境下会被安全策略拦截，**实测会让 dev server 直接崩溃**（与 3.5 的 mock 问题同源：都是「依赖删除动作」的设计缺陷）；
   - 全量注册后依赖图恒定，产物 CSS 只有一份（约 356 KB），dev server 不再抖动。
   - 若要进一步瘦身，应改为「按需引入 + 组件级 CSS」并**去掉**全局 `index.css`——两者只能取其一，不可同时启用。

### 3.8 优缺点与契合度

- **优点**：零额外心智负担、一次安装一次部署、`common` 直接跨系统复用、调试简单、契合答题纸 `views/admin + views/before` 结构；
- **缺点**：两子系统耦合在同一构建产物，无法独立发布；依赖体积偏大；不体现工程化「分包」亮点；
- **契合度**：系统设计 25% → 良好；核心实现 30% → 优秀；
- **推荐指数**：★★★★★

## 四、方案二：pnpm workspace Monorepo

### 4.1 方案定位

> **一个仓库、多个包：`apps/admin` 与 `apps/storefront` 独立构建独立启动，公共能力抽到 `packages/shared`。**

| 项 | 内容 |
| --- | --- |
| 适用场景 | 想展示工程化能力、需要「独立构建/独立部署」加分、3 人以上分工明确 |
| 新手难度 | ★★★☆☆（3/5） |
| 工程数量 | 2 个 app + 2~3 个 package |

### 4.2 目录结构

```

│     └─ package.json
```

### 4.3 路由设计

路由**内容与方案一完全一致**，差异仅在「归属哪个 app + basePath」：

| 归属应用 | basePath | 路由范围 | 注册方式 |
| --- | --- | --- | --- |
| `apps/admin` | `/admin` | 后台全表（login / dashboard / category / goods / order / profile，含 admin Layout 嵌套） | `createRouter({ history: createWebHistory('/admin') })` |
| `apps/storefront` | `/` | 前台全表（before Layout 嵌套 + login / register + 404） | `createRouter({ history: createWebHistory('/') })` |
| 跨应用跳转 | — | 「后台入口」「退出」等 | 绝对 URL（dev 下 admin:5173 / storefront:5174）或反向代理统一域名 |

每个 app 只含自己那半张路由表；`router/guard.js` 的鉴权逻辑抽到 `@ecom/shared` 复用。

### 4.4 Pinia 模块划分

- **共享 store（`packages/shared/src/store`）**：`user`（登录态 / token / 角色）、`app`（主题 / 布局）；
- **应用私有 store**：`apps/admin/src/store` → `category` / `goods(admin)` / `order(admin)`；`apps/storefront/src/store` → `cart` / `goods(front)` / `order(front)` / `favorite`；
- 共享 store 由 `@ecom/shared` 导出 `useUserStore`，各 app `createPinia()` 后 `use()` 即可；持久化插件在 shared 内注册，保证两 app 行为一致。

### 4.5 Mock 层设计

- 抽成 `@ecom/mock` 包，两 app 的 `vite.config` 引入同一 mock 配置 → **一套数据两处生效**；
- 此方案下 `json-server` 更划算：可跑一个独立 mock 服务，两 app 连同一 `baseURL`，更接近真实「独立前后端」；
- `@ecom/shared/src/api/request.js` 暴露 `createRequest(options)` 工厂，各 app 传入自己的 `baseURL` / 拦截逻辑；业务代码仍只认 `request`。

### 4.6 组件复用策略

- **跨应用复用** → `@ecom/shared/src/components`（DataTable、FormDialog、SearchForm、Pagination、ImageUpload、StatusTag、EmptyState）；
- **应用内业务组件** → 各 app 的 `components/`；
- **样式与主题** → `@ecom/shared/styles`，两 app 统一引入，避免视觉分裂；
- 复用方式：`import { DataTable } from '@ecom/shared'`（workspace 协议）。

### 4.7 关键技术点

1. pnpm workspace 依赖提升与 `workspace:*` 协议；
2. `shared` 包分发策略：源码直接引用（`exports` 指向 src）vs lib 模式预构建的取舍；
3. 多 app 请求层工厂化：`createRequest` 统一拦截器，双 app 独立实例 + 共享契约；
4. 独立构建与 Element Plus 按需引入在 monorepo 下的集中配置。

### 4.8 优缺点与契合度

- **优点**：真正的「独立开发、独立构建、独立部署」，工程化亮点强，复用规范，易于团队分工；
- **缺点**：配置门槛高（workspace 协议、包导出、跨包样式/HMR 问题），排错成本高；
- **契合度**：系统设计 25% → 优秀；核心实现 30% → 良好（工程配置吃掉部分精力）；
- **推荐指数**：★★★☆☆

## 五、方案三：微前端（qiankun / wujie）

### 5.1 方案定位

> **主应用（基座，负责布局、鉴权、路由调度）+ 后台子应用 + 前台子应用，三者独立开发、独立部署、运行时组合。**

| 项 | 内容 |
| --- | --- |
| 适用场景 | 想拿「架构设计」高分、答辩有亮点；团队分工极清晰（一人一应用） |
| 新手难度 | ★★★★★（5/5） |
| 工具建议 | `wujie`（无界）比 `qiankun` 更简单、iframe 沙箱、对 Vite 子应用支持更友好；若教材已教 qiankun 则用 qiankun |

### 5.2 目录结构

```
ecommerce-micro/
├─ main/                               # 主应用（基座）
│  ├─ src/
│  │  ├─ main.js                       # 注册子应用
│  │  ├─ App.vue                       # 基座外壳 <router-view> + 微应用容器
│  │  ├─ micro/
│  │  │  ├─ apps.js                    # 子应用注册表（name / entry / activeRule / container）
│  │  │  ├─ MicroApp.vue               # 通用挂载容器组件
│  │  │  └─ state.js                   # 全局共享状态下发（token / user / theme）
│  │  ├─ layout/                       # 顶层布局（决定后台/前台骨架切换）
│  │  ├─ router/                       # 基座路由（/admin/* 与 / 分别激活子应用）
│  │  ├─ store/                        # 全局 user / app / permission
│  │  └─ auth/                         # 统一鉴权、登录页、token 管理
│  ├─ vite.config.js
│  ├─ index.html
│  └─ package.json
├─ sub-admin/                          # 子应用：后台管理
│  ├─ src/{main.js, App.vue, router/, store/, views/, components/, api/}
│  ├─ vite.config.js                   # base、允许跨域、output 为 UMD/ESM
│  └─ package.json
├─ sub-storefront/                     # 子应用：电商前台
│  ├─ src/{main.js, App.vue, router/, store/, views/, components/, api/}
│  ├─ vite.config.js
│  └─ package.json
└─ packages/
   └─ shared/                          # 共享：组件 / 工具 / 请求封装 / 常量 / 全局状态契约
      ├─ src/
      └─ package.json
```

### 5.3 路由设计（主 + 子）

| 层级 | path | 归属 | 路由 / 激活规则 | 说明 |
| --- | --- | --- | --- | --- |
| 主应用 | `/` | main | 基座路由，默认跳 `/home` | 决定加载哪个子应用 |
| 主应用 | `/admin/*` | main | `activeRule: '/admin'`（qiankun）/ `MicroApp url`（wujie） | 激活后台子应用 |
| 主应用 | `/*` 其余 | main | `activeRule: '/'` | 激活前台子应用 |
| 主应用 | `/login`、`/register` | main | 基座内实现 | 统一登录，token 下发子应用 |
| 子应用 sub-admin | `/admin/login`、`/admin/dashboard`、`/admin/category` … | sub-admin | 内部 `createWebHistory('/admin')` | 内容同 3.3 后台表 |
| 子应用 sub-storefront | `/home`、`/search`、`/goods/:id`、`/cart` … | sub-storefront | 内部 base `/` | 内容同 3.3 前台表 |

**要点**：主子应用路由必须**错开 activeRule**，避免互相抢占；后台子应用用带前缀的 history；前台子应用注意与基座路由不冲突。

### 5.4 Pinia 模块划分（跨应用）

- **主应用全局 store**：`user`（token / 角色）、`app`（主题 / 布局）、`permission`（可访问子应用 / 菜单），**作为唯一数据源**，通过 props 或 qiankun `initGlobalState` / wujie `bus` 下发给子应用；
- **子应用私有 store**：sub-admin → `category` / `goods` / `order`；sub-storefront → `cart` / `goods` / `order` / `favorite`；
- **契约**：子应用启动时从主应用注入的 `user` 读取 token 注入自己的 axios 实例，子应用内不再自行维护登录态，避免状态分裂。

### 5.5 Mock 层设计

- **选型**：推荐 `json-server` / 独立 mock 服务——主子应用都能通过统一 `baseURL` 访问同一 mock 服务，模拟真实多端后端；
- **组织**：`packages/shared/src/api` 提供 request 工厂；根目录 `mock-server/`（json-server + 路由重写）提供数据；
- **解耦**：每个子应用用 `createRequest({ baseURL })` 建实例；主应用把 `baseURL`、`token` 注入子应用；切换真实接口只改 env。

### 5.6 组件复用策略

- **共享包**：`packages/shared` 提供 common 组件、composables、utils、request、常量（与方案二同构）；
- **业务组件**：各子应用内维护，避免跨子应用耦合；
- **UI 一致性**：Element Plus 版本、主题、全局样式在 shared 统一定义；
- **通信**：主 ↔ 子用 props/全局状态；子 ↔ 子用主应用事件总线（尽量少，避免强耦合）。

### 5.7 关键技术点

1. 子应用注册与生命周期（qiankun `registerMicroApps` / `loadMicroApp`；wujie `<MicroApp>`）：entry、activeRule、container、mount/unmount；
2. 全局状态与鉴权下发：`initGlobalState`（qiankun）或 `bus`（wujie），子应用请求层注入；
3. 沙箱与样式隔离：JS 沙箱（快照 / Proxy）、CSS 隔离（strictStyleIsolation / Shadow DOM）与 Element Plus 冲突处理；
4. 资源路径与部署：子应用 `base` / `publicPath`、跨域、独立域名 / 子路径部署与 CORS。

### 5.8 优缺点与契合度

- **优点**：架构设计满分亮点，独立部署、技术栈可异构、团队并行，答辩演示价值高；
- **缺点**：复杂度最高，沙箱 / 样式 / 路由冲突排错极费时，工期下**极易翻车**（时间多耗在框架集成而非业务功能）；
- **契合度**：系统设计 25% → 优秀；核心实现 30% → 及格~良好（业务时间被压缩，功能完整度风险大）；
- **推荐指数**：★★☆☆☆

## 七、落地推荐

**强烈推荐「方案一：单工程路由分区」作为实际落地方案。**

1. **性价比最高**：答题纸评分重心是「核心功能实现 30% + 系统设计 25%」。方案一能用最少的时间把**全部功能点做完整、做扎实**（Token 鉴权、路由拦截、四类 CRUD、多条件筛选、图片上传、批量上下架、订单状态、ECharts 聚合），而不是把时间烧在脚手架配置上。
2. **结构天然对齐答题纸**：`views/admin`、`views/before`、`components`、`router`、`assets`、`main.js` 目录示例本就按单工程书写，答辩时可与考核要求一一对应，评委易理解。
3. **保留全部加分项**：虽为单工程，但通过 `components/common` + `composables` 的分层复用、`router/modules` 分区、`api` 分包，仍能写出高质量的「系统设计」章节（分层图、路由表、组件设计齐全）。
4. **风险最低**：纯前端 + Mock + 单工程，环境问题最少，演示最稳。

**论文写作策略建议**：以方案一为主线实现；在「系统设计」章节把方案二 / 方案三作为**架构演进讨论**——"若后续需要独立部署或多团队协作，可平滑升级为 Monorepo 或微前端"，既体现思考深度，又不承担实现成本，是**拿分最优策略**。
